# KVEngine 工业级协作规范

这个仓库是一个 C++ KV 存储引擎，包含 `memtable`、`WAL`、`SSTable`、`cache`、`txn`、`raft`、`net` 等模块。
在这个仓库里协作时，默认按工业级工程标准处理。

先查看 [.claude/MODULES.md](/Users/aiziqi/Desktop/KV_/.claude/MODULES.md)，按模块定位检查点和测试范围。

## 目标优先级

1. 正确性
2. 可验证性
3. 可回滚性
4. 最小改动
5. 性能
6. 代码整洁度

## 默认工作流

1. 先读代码、测试和文档，确认现有语义。
2. 找到入口、调用链和状态流。
3. 构造最小复现或最小失败测试。
4. 只修改必要的代码路径。
5. 补回归测试。
6. 编译并运行相关测试。
7. 再决定是否需要扩大修复范围。

## 模块优先级

- 存储主链路：`engine/` -> `wal/` -> `memtable/` -> `sstable/` -> `version/`
- 对外接口：`net/` -> `engine/`
- 分布式链路：`raft/` -> `engine/` -> `wal/` / `sstable/`
- 上层数据结构：`data_types/` -> `engine/`
- 横切关注：`cache/`、`txn/`、`concurrency/`、`cluster/`

## 业务拓展顺序

如果当前任务是继续拓展业务，优先顺序建议是：

1. `engine/`：先把核心存储语义做稳。
2. `net/`：再把对外协议和会话能力做完整。
3. `cluster/`：最后把路由、节点和副本治理做强。
4. 其余模块按具体需求补齐。

针对 `engine/`、`net/`、`cluster/` 的新业务扩展，默认要求先补模块级测试，再考虑跨模块联动。

## 修改规则

- 修改必须围绕明确问题，不做无关重构。
- 任何会改变持久化格式、读写顺序、序列号、锁语义、协议兼容性的改动，都要显式说明风险。
- 触碰 `WAL`、`recovery`、`flush`、`compaction`、`snapshot`、`raft`、`transaction` 时，默认按高风险路径处理。
- 不要为了“顺手”改公共接口、配置格式或目录结构。
- 如果一个修复涉及多个模块，先验证模块边界，再提交跨模块改动。

## 必做验证

- `cmake --build build`
- `ctest --test-dir build --output-on-failure`

如果改动只影响局部模块，优先跑相关测试子集，再补全局测试。

## 高风险检查点

- 持久化路径：写入顺序、恢复顺序、幂等性、崩溃后状态一致性。
- 并发路径：锁顺序、死锁、可见性、事务冲突、读写隔离。
- 协议路径：输入解析、错误返回、兼容旧请求、边界帧处理。
- SST/Compaction：序列号比较、跨 block 读取、墓碑处理、文件回收。
- RAFT：leader/follower 语义、日志复制、提交确认、重启恢复。

## 测试要求

- 修 bug 必须补回归测试。
- 修复持久化或恢复问题时，必须覆盖重启场景。
- 修复并发问题时，必须覆盖冲突或竞争场景。
- 修复协议问题时，必须覆盖非法输入和边界输入。

## 代码标准

- 优先使用明确的状态返回，不要吞错。
- 不要引入“看起来能跑”的猜测逻辑。
- 保持数据结构和状态机的可解释性。
- 新增代码应尽量复用现有抽象，不要重复实现。

## 对外输出标准

- 先给结论，再给影响范围，再给验证结果。
- 文件引用尽量使用绝对路径。
- 如果执行了测试，要明确列出命令和结果。
- 如果还有残余风险或未覆盖路径，要直接说明。

## 不要做的事

- 不要默认删除 `.claude` 下现有文件。
- 不要无故清理用户未要求的改动。
- 不要在没有测试或证据时断言“应该没问题”。
- 不要把局部问题扩大成不必要的重构。
