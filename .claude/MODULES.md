# KVEngine 模块地图

这个文件用于把仓库拆成可检查的工程模块。后续辅助工作时，优先先定位到对应模块，再决定测试和修改范围。

## 模块总览

- `engine/`：DB 生命周期、读写入口、恢复、快照、flush、compaction、事务接入。
- `memtable/`：内存态写入结构、迭代、序列号可见性。
- `wal/`：日志编码、写盘、恢复、崩溃一致性。
- `sstable/`：块编码、索引、过滤器、table reader/builder、缓存读取。
- `version/`：manifest、版本集合、文件管理、compaction 结果提交。
- `cache/`：读缓存、TTL、淘汰策略、统计信息。
- `txn/`：事务隔离、冲突检测、提交/回滚。
- `raft/`：复制、状态机应用、领导者语义、重启恢复。
- `net/`：命令解析、协议编码/解码、session 生命周期、服务器连接管理。
- `cluster/`：路由、hash ring、节点状态、分片/副本选择。
- `data_types/`：hash、list、counter 这类上层数据类型实现。
- `concurrency/`：线程池、锁、阻塞队列、并发原语。

## 业务扩展优先级

如果当前需求是“继续拓展业务”，优先顺序建议是：

1. `engine/`：先把核心存储语义做稳。
2. `net/`：再把对外协议和会话能力做完整。
3. `cluster/`：最后把路由、节点和副本治理做强。
4. 其余模块按需要并行补齐。

## 按模块的检查点

### `engine/`

- 写入是否先持久化再暴露。
- 恢复后状态是否和 WAL / SST 一致。
- snapshot、transaction、cache、compaction 的联动是否完整。
- 任何写路径是否正确处理失败回滚。

#### 业务拓展点

- 增加新的 DB 能力时，优先放在 `engine/` 的统一入口，再向下拆到 `wal/`、`memtable/`、`sstable/`。
- 如果要支持新的读写语义，先明确它是否受 snapshot、transaction、cache 影响。
- 如果要新增后台任务，先明确它是否会影响 flush / compaction / recovery 的状态机。
- 如果要增加统计或管理接口，优先挂到 `engine/`，再决定是否透出到 `net/` 或 `cluster/`。

### `memtable/`

- 相同 key 的版本顺序是否正确。
- 删除墓碑是否能正确屏蔽旧值。
- 迭代是否稳定、可预测。
- 序列号边界是否正确处理。

### `wal/`

- 编码和解码是否完全对称。
- 部分写入、截断、损坏是否能检测。
- Sync / Close 是否有明确语义。

### `sstable/`

- block 边界、restart point、前缀压缩是否正确。
- index / filter / footer 的位置和长度是否一致。
- 点查是否能跨 block 找到最新可见版本。
- compaction / iterator 是否能处理墓碑和重复 key。

### `version/`

- manifest 追加和恢复是否幂等。
- 文件添加/删除是否能重建当前视图。
- 文件编号和序列号是否能正确递增。

### `cache/`

- 命中、失效、淘汰、TTL 是否一致。
- 写路径是否能正确失效旧缓存。
- 统计指标是否反映真实行为。

### `txn/`

- 读写集合是否能正确检测冲突。
- commit / rollback / destructor 是否保持状态一致。
- 多次操作的可见性是否符合事务语义。

### `raft/`

- 提议、复制、提交、应用是否按 leader 语义推进。
- follower / candidate / leader 的状态切换是否完整。
- 重启后日志和状态机是否能恢复到一致状态。

### `net/`

- line 协议和 RESP 协议是否都能正确解析。
- 半包、粘包、错误帧是否能被正确处理。
- session 中 transaction / non-transaction 路径是否分离清楚。

#### 业务拓展点

- 增加命令时，先定义命令语义，再扩展 parser、codec、session、executor。
- 如果命令依赖事务，必须明确 BEGIN/EXEC/ABORT 路径。
- 如果命令依赖快照或线性一致性，必须明确读路径是否要走 `engine/` 的快照接口。
- 如果命令会返回结构化数据，先定义协议格式，再实现编码和测试。
- 所有新命令都要覆盖非法参数、空参数、边界参数和错误路径。

### `cluster/`

- 节点存活状态是否影响路由。
- 副本选择是否稳定且无重复。
- hash ring 的边界和空集处理是否正确。

#### 业务拓展点

- 扩展集群能力时，先明确 routing、node status、replica policy 三者的边界。
- 如果要做多副本读写分流，先定义 leader / follower / replica 的责任，不要只改路由表。
- 如果要引入故障转移，要明确节点失活、重试、回退和一致性语义。
- 如果要增加集群管理命令，优先设计成幂等操作，避免重复执行带来状态漂移。
- 集群相关改动必须验证空集、单节点、多节点、节点失活、节点恢复这五类场景。

## 验证策略

- 只改一个模块时，先跑这个模块相关测试。
- 跨模块改动时，先跑局部测试，再跑全量测试。
- 任何涉及持久化/恢复/协议的改动，都要至少验证一次重启或重读场景。
- 任何涉及并发的改动，都要验证冲突或竞争路径。

## 触发建议

- 如果问题明确落在一个模块，先只看对应章节。
- 如果要继续拓展业务，优先从 `engine/` 开始，再推进到 `net/` 和 `cluster/`。
- 如果问题横跨多个模块，先看 `engine/`，再向下分解到 `wal/`、`sstable/`、`version/`、`cache/`、`txn/`、`raft/` 或 `net/`。
